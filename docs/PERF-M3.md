# M3 并发压测实验记录（虚拟线程 / SSE 长连接）

> 本文档记录了一次**测量方法本身出错**的完整经过 —— 结论部分只写**用正确方法复测后**的数据。
> 环境：WSL + Windows 单机；应用 `java -jar`（JDK 25 / Boot 3.5.16）；假上游 Python 3.11。

## 0. 结论速览

| 指标 | 数值 |
|---|---|
| 单条 SSE（2 轮模型调用，假上游 1.8s/轮） | **3.81s**（12 个 delta，真流式） |
| 并发 24（VT ON，OkHttp 默认） | **14.43s**（24/24 成功，全部带 delta） |
| 并发 64（VT ON，OkHttp 默认） | **26.10s**（64/64 成功，全部带 delta） |
| 并发 24（VT **OFF**，OkHttp 默认） | **12.35s**（3 次均值） |
| 并发 64（VT **OFF**，OkHttp 默认） | **27.08s**（3 次均值） |
| 并发 24（VT ON，OkHttp 调优） | 12.96s |
| 并发 64（VT ON，OkHttp 调优） | 27.30s |

**有效结论**：
1. SSE 长连接链路在并发下**可用**（24/64 并发零失败，且每个请求都带 delta = 真流式）。
2. **虚拟线程在本场景没有收益**（24 并发略慢 7%、64 并发无差异，各 3 次测量）。
   推断原因：**瓶颈不在线程**（并行度只有 7~9），线程不是瓶颈时换虚拟线程自然无效。
3. **并发上限不是 OkHttp 连接池**（调优 vs 默认：12.96 vs 14.43、27.30 vs 26.10，都在噪声内）。
4. 真正的上限**未定位**。主要嫌疑：**假上游自身**（Python `ThreadingHTTPServer` + GIL），
   即这些数字是「应用 + 假上游」的**合成结果**，不能单独归给应用。

## 1. ⚠️ 前两版测量方法都是错的（这是本次最有价值的部分）

| 版本 | 做法 | 缺陷 | 症状 |
|---|---|---|---|
| v1 | `powershell -Command "curl.exe ..."` 并发 | **每个请求都启一个 PowerShell 进程**（~1-2s 启动开销） | 2 并发也要 18.82s |
| v2 | `curl -o /dev/null -w '%{time_total}'` | SSE 是**异步**的：`time_total` 只测到**响应头**，流还在后面 | 报出 0.03s（假的"很快"） |
| v3（现行） | `curl.exe -o <文件> -w '%{time_total}'`，读**完整流** | — | 单发 3.81s，与理论一致 |

**v1 造成的直接后果**：我据此得出「64 并发要 171s」并**推断「瓶颈是 OkHttp 连接池」**，
甚至按这个推断改了代码。用 v3 复测后：**默认与调优几乎无差** → **推断不成立，改动已回退**。

> 📌 **教训**：与今天其它几次同源 ——
> `unzip` 不存在导致假阴性、`grep -v` 把中文当二进制、javap 正则漏 `Retries`、
> 截图用文本而非元素判定、测试正则转义写错导致假绿……
> **共同点：都没有先验证「我的观察手段本身是否有效」。**
> 压测这类性能实验尤其危险 —— 出错时数字看起来仍然"像那么回事"，不会报错。

## 2. 第一次压测（只读页面）—— 只能证明「能用」

`bash ops/loadtest.sh http://127.0.0.1:28091 32 100`

| 阶段 | 总请求 | QPS | p50 | p95 | 2xx |
|---|---|---|---|---|---|
| 首页（Redis 缓存） | 1920 | 42.0 | 16ms | 403ms | 100% |
| 搜索页（DB） | 1920 | 34.1 | 108ms | 1227ms | 100% |
| 商品分类页（DB+模板） | 1920 | 24.9 | 1078ms | 1540ms | 100% |

**边界**：只读页面 IO 少、本来就不吃线程，**压它证明不了虚拟线程的价值**（claude 复核时指出）。
另外该脚本统计的是「HTTP 200 数量」，**不能区分"真成功"与"静默失败"**（后者的 200 也计数）。

## 3. 第二次压测（SSE + 本地假上游）—— 有意义的对照

真模型不可控（agnes 免费额度会 429，混进来会把「本应用吞吐」和「上游限流」搅在一起），
所以写了 `ops/fake_upstream.py`：本地 OpenAI 兼容假上游，**慢速流式**（12 chunk × 150ms ≈ 1.8s/次）。
客服每请求走 **2 轮**模型调用（第一轮定工具 → 查库存 → 第二轮生成），故单请求 ≈ **3.6s**。

### 3.1 虚拟线程 ON/OFF 对照（v3 正确方法，各跑 3 次）

| 并发 | VT ON（3 次） | VT OFF（3 次） | 均值对比 |
|---|---|---|---|
| 24 | 12.96 / 14.43 / 12.40 → **均值 13.26s** | 12.09 / 12.49 / 12.47 → **均值 12.35s** | VT OFF 反而**略快**（-7%） |
| 64 | 27.30 / 26.10 → 均值 26.70s | 27.63 / 26.74 / 26.88 → 均值 27.08s | **无差异**（±1.4%） |

**结论：在本场景下，虚拟线程没有带来收益（24 并发时甚至略慢）。**

⚠️ **这个结论差点被我写反**：VT OFF 的**第一次**测量是 17.75s，据此会得出
"VT ON 快 23%" 的正向结论；**复测 3 次后发现那是个异常值**（很可能是启动后的冷启动），
真实均值 12.35s 反而比 ON 更低。**单次测量不足以支撑性能结论** —— 本次是"复测救了一次误判"的正面案例。

**为什么没有收益（推断，与本场景的特征一致）**：
客服链路虽然 IO 密集，但**本实验的瓶颈根本不在线程** —— 从 §0 的并行度只有 7~9 就能看出，
真正卡住的是下游（假上游 / DB 连接池 / 平台其他限制）。
**线程不是瓶颈时，换虚拟线程自然没有收益。**

> 早期 v1 方法测出的「ON 47s / OFF 57s」「ON 171s / OFF 192s」**已作废**（见 §1）。

### 3.2 假上游的坑（顺带记录）

假上游最初用了 `Connection: keep-alive` 且不关闭连接 → 客户端**永远等不到流结束**，
表现是 curl 撞 `-m` 超时、应用侧报「模型流式调用超时」。
SSE 响应没有 `Content-Length`，**客户端只能靠连接关闭判断结束** → 必须 `Connection: close` + 显式关闭。
修好后假上游单发 1.85s（与设计一致）。
