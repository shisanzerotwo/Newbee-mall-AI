# RAG 评测（RAG-EVAL）

> **这份文档回答**：我们的检索**到底行不行**、怎么量的、换模型有没有用、怎么复跑。
> 原始实验记录在 `PERF-M3.md`（含方法论翻车记录）；这里给**结论与可复跑的流程**。

---

## 1. 评测口径（先说清"怎么算对"，否则数字没意义）

### 1.1 为什么需要两套用例

| 组 | 例子 | 关键词（2-gram）通路能命中吗 | 用途 |
|---|---|---|---|
| **同词查询** | 问「化妆水」（商品标题也叫化妆水） | **能** | 看链路是否正常 —— **但区分不出嵌入模型** |
| **语义查询** | 问「补水的护肤水」（标题里没有这个词） | **不能** | **只有向量语义能救** → 这组才区分得出模型 |

> ⚠️ **这是第一版评测踩的坑**：只用了同词组，两个模型**都是 40%、毫无差异**，
> 差点得出「换模型没用」。**评测口径决定了你能不能看出差异。**

### 1.2 判定方式

对每个查询，看检索结果 **Top-3 片段文本里是否出现该类目的期望关键词**；
统计 `命中数 / 总数`。

口径粗（关键词命中 ≠ 语义正确），但**可复算、不随人"感觉"漂移**，足以支撑"换不换模型"的决策。

### 1.3 ⚠️ 分母陷阱与「可满足子集」（2026-09-19 新增，读数字前必读）

**原始 20 条用例里，有 11 条的期望关键词在整个语料里根本不存在。**
商品库一共 575 件：**276 台手机 + 256 件未分类 + 40 支口红 + 3 台扫地机器人** ——
**没有面膜 / 防晒 / 眼霜 / 香水 / 精华 / 洗发水 / 洁面膏这些类目**。
拿这类用例当分母，等于**给分母灌水**：检索再准也不可能命中，40% 里有很大一块是"题目本身无解"。

所以本评测**同时给两个指标，两份都如实记录、不互相取代**：

| 口径 | 定义 | 用途 |
|---|---|---|
| **口径一 · 原始全量** | 10 + 10 条**一条不删**，如实记录 | 历史口径，便于跟换模型前后的数字纵向对比 |
| **口径二 · 可满足子集** | 只保留「期望关键词在语料中至少出现一次」的用例 | 度量**检索能力本身**，不被无解题拉低 |

「可满足」由评测代码在运行时**扫全量语料动态判定**（`RagChineseQualityTest#satisfiable`），
**不是人工挑的** —— 想挑对自己有利的用例，代码不允许。
注意它是**必要不充分**条件：关键词在语料里存在，不代表检索一定能把它排进 Top-3
（语义组第 2 条「洗完脸用来擦的」就是反例，见 §2.3）。

## 2. 结果（实测）

### 2.1 嵌入模型 A/B

> 下表的 40% / 20% 都是**口径一（原始全量，含无解用例）** —— 是历史数字，保留以便纵向对比。
> **口径二的真实检索能力见 §2.3。**

| 模型 | 维度 | 同词查询 | **语义查询** |
|---|---:|---:|---:|
| `all-MiniLM-L6-v2`（英文） | 384 | 4/10 = 40% | **2/10 = 20%** |
| **`bge-small-zh-v15`（中文）** | 512 | 4/10 = 40% | **4/10 = 40%** ← **翻倍** |

**结论**：
1. **同词查询两组相同** → 混合检索的关键词通路**已经兜住了**，向量模型差异被掩盖
2. **语义查询中文模型是英文的 2 倍** → 中文模型的价值**真实存在**，且只在语义场景体现
3. → **默认切到中文模型**（`cs.rag.embedding-model` 默认 `bge-zh`，仍保留可切换）

**代价与收益**：维度 384→512（索引略大）；收益是口语化/同义查询命中率翻倍 ——
客服场景用户说话本来就口语化，**值得**。

### 2.2 语料红线（结构性保障，非 prompt 兜底）

| 检查项 | 结果 |
|---|---|
| 写入向量库的 chunk 是否含**结构化价格 / 库存字段**（`价格：` / `库存：`） | **0 命中**（588 片段）✅ 红线成立 |
| chunk 中**裸词**「价格」 | 2 条 —— 均为**欧莱雅品牌文案**（"以合理的价格…"），非价格数据 |
| chunk 中**裸词**「元」 | 15 条 —— 来自**商品名与详情文案**（如"荣耀 8X 千**元**屏霸"、"三**单元**发声"），**不是泄漏** |
| 建库总片段数 | 588（575 商品 + 分类等） |

> **口径要说清楚**（2026-09-19 修正）：红线是「**不写入结构化价格/库存字段**」，
> 不是"文本里不许出现『价格』这两个字"。上面三个数字要放在一起读才诚实：
> **结构化字段 0 命中**才是红线的判据；裸词 2 条 / 15 条是商品名与品牌文案的自然语言，
> 不构成"把价格写进语料"。**别把裸词计数当成红线被破**，也别拿结构化字段的 0 去掩盖裸词。

**为什么必须这样**：Python 教学版 609 个片段里 **575 段**正文写死了「价格：X 元 / 库存：N 件」，
注入 prompt 时会与工具查询结果**冲突**。本项目的「数据铁律」是：
**价格/库存/订单状态一律以工具查询为准，RAG 只作语义参考** —— 所以从**清洗阶段**就不写这几个字段。

> ⚠️ **复核这份语料时的踩坑（2026-09-19）**：必须用 `redis-cli` 的 **raw 模式**，并**先做阳性对照**。
> `--no-raw` 会把中文转义成 `\xNN`，此时 `grep 价格` **永远 0 命中** —— 空跑却伪装成"红线通过"。
> 阳性对照：`grep 商品名称` 应命中文档数（实测 575）。详见 `DEVELOPMENT.md` §4 调试手法。

### 2.4 RRF 参数 A/B（候选集 × 权重，2026-09-19）

被 A/B 的三个参数（都做成了 `@Value`，默认值 = 改动前的历史行为）：

| 参数 | 默认 | 含义 |
|---|---|---|
| `cs.rag.keyword-candidates` | 10 | 关键词侧取多少候选参与融合 |
| `cs.rag.vector-candidates` | 0（= `max(topK*2, 5)`） | 向量侧候选数；>0 时取绝对值 |
| `cs.rag.keyword-weight` | 1.0 | RRF 中关键词侧权重（1.0 = 与向量等权） |

| 变体 | 原始全量 | 可满足子集 |
|---|---|---|
| 默认（基线） | 8/20 = 40.0% | **8/9 = 88.9%** |
| `keyword-candidates=30` | 8/20 = 40.0% | 8/9 = 88.9% |
| `vector-candidates=20` | 8/20 = 40.0% | 8/9 = 88.9% |
| 两者同时扩大 | 8/20 = 40.0% | 8/9 = 88.9% |
| `keyword-weight=0.5` | 8/20 = 40.0% | 8/9 = 88.9% |
| **`keyword-weight=2.0`** | 7/20 = 35.0% | **7/9 = 77.8%** ← **回归** |

**结论：本轮 C（扩候选集 + 调权重）没有任何正收益，故不动默认值。**
逐条机制（都有实测证据，不是"感觉"）：

1. **旋钮确实生效**（否则"没变"可能是空跑，必须排除）——
   - **候选数**：`-Dlogging.level.ltd.newbee.mall.service.agent.RagService=DEBUG` 实测，
     关键词候选从「≤10」（基线）变成 `30/26/18/16/12` 都出现过；向量侧恒为 6，与 `max(3*2,5)` 吻合。
     → 这条任何人都能复跑。
   - **权重**：`keyword-weight=2.0` 让指标从 8/9 掉到 7/9（见下面第 4 点），
     说明该字段确实被读到 —— 一个恒不被读取的参数不可能改变结果。
   - 另有一次**一次性临时探针**（已删除、**非交付物**）直接打印 Spring 绑定到的三个字段值，
     实测 `keyword-candidates=30 vector-candidates=20 keyword-weight=0.5` 全部正确读到；
     它只是省事，不是必要证据（上面两条已足够）。
2. **扩向量候选对 Top-3 近似恒等**：`maxResults` 从 6 增到 20 只延长有序列表，
   前 3 名顺序不变 → 不改变融合前 3（除非关键词侧挤进来，实测没挤）。
3. **扩关键词候选挤不进前 3**：新增候选的 RRF 分是 `1/(60+rank) ≤ 1/70 ≈ 0.0143`，
   而向量侧 Top-1 恒为 `1/60 ≈ 0.0167` —— 分差在量级上就不够。
4. **权重 2.0 为什么回归**：关键词分翻倍后，2-gram 命中的样板噪声压过向量侧正确项，
   「洗脸用的清洁产品」从命中翻成未命中（8/9 → 7/9）。**这就是阴性对照**：
   把参数改回 1.0，指标立刻回到 8/9。
5. **权重 0.5 为什么不涨**：它确实**改变了 Top-3 内部排序**（见下），
   但本口径只看"Top-3 里有没有期望词"，**对排序不敏感** → 指标不动。

**顺带发现的一个真问题（本轮未改，留证）**：
关键词通路会被**词面噪声**命中，让**无关商品**拿到与向量侧 Top-1 **打平**的分数（都是 `1/60`）；
而 RRF 用 `LinkedHashMap` 先插入关键词侧、`sorted` 又是稳定排序，
**平局时关键词侧"先插先赢"** → 无关商品直接坐上 Top-1。噪声来源实测有两类：

- **样板文本**：`详情：商品介绍加载中…`、`产品信息 Product Information` 里的
  「产品 / 商品 / 信息」等词，会被大量商品的 2-gram 命中（「洗脸用的清洁产品」的 9 条候选多半来自这里）
- **长品牌文案**：如欧莱雅品牌介绍是长篇护肤营销文，会被「补水 / 护肤 / 肤水」命中

| 查询 | 默认 `weight=1.0` 的 #1 | `weight=0.5` 的 #1 |
|---|---|---|
| 补水的护肤水 | 欧莱雅**唇膏**（无关） | 无印良品**化妆水**（正确） |
| 洗脸用的清洁产品 | 小米**手机**（无关） | 无印良品**洁面泡沫**（正确） |

**怎么证明噪声来自关键词侧而不是向量侧**：降权到 0.5 后两者都翻正 ——
若 #1 是向量侧贡献的，降低关键词权重**不会**改变它（向量侧分数恒为 `1/60` 不受影响）。
所以这两条 #1 确系关键词侧贡献 ✅。

即：**默认参数下 2 组查询的 Top-1 是错的商品，只是"正确的商品还在 Top-3 里"，布尔口径看不出来。**
降权能修，但没有指标能证明它值得改 → **按"收益是真的 ≠ 该做"暂不动默认值**，
先把度量补上（见 §4 局限第 1 条）。

### 3.1b 调参 A/B 怎么跑（§2.4 就是这么做出来的）

```bash
# 变体 = 加 -D（默认值见 §2.4 表；不传就是历史行为）
bash ops/mvn.sh test -Dtest=RagChineseQualityTest \
  -Dcs.rag.keyword-candidates=30 -Dcs.rag.vector-candidates=20 -Dcs.rag.keyword-weight=0.5

# 想看到"候选到底取了多少条"，开这个开关（RagService 的 DEBUG 日志）
bash ops/mvn.sh test -Dtest=RagChineseQualityTest \
  -Dlogging.level.ltd.newbee.mall.service.agent.RagService=DEBUG
```

> ⚠️ **跑 A/B 前必做**：先确认参数**真的生效**，否则"指标没变"可能是空跑。
> 本项目的做法是打印 Spring 实际绑定到的值（`-D` 有没有被 WSLENV 漏掉、key 有没有写错）。
> 判据：`keyword-candidates=30` 时 DEBUG 日志里应出现 `关键词 30 条` 之类 >10 的数字。

### 3.2 换模型做 A/B（**必须重建索引**）

```bash
# ① 先停应用！否则它会继续往已删索引写 → hash_indexing_failures 爆表
#    而"检索居然还能返回结果"，极易误判为"索引是好的"

# ② 删索引
docker exec newbee-mall-redis redis-cli FT.DROPINDEX goods_kb

# ③ 指定模型并启动（KnowledgeBuilder 会按新维度重建）
export CS_RAG_EMBEDDING_MODEL=bge-zh      # 或 minilm
bash ops/mvn.sh spring-boot:run

# ④ 验证重建正确（⭐ 三个都要看）
docker exec newbee-mall-redis redis-cli FT.INFO goods_kb
#   dim = 512                              ← 与模型匹配
#   num_docs = 588                         ← 全部商品
#   hash_indexing_failures = 0             ← ⭐ 关键判据
```

> ⚠️ **判据教训**：只看 `num_docs` 会被"部分失败"骗过 ——
> 实测遇到过 `num_docs=588` 但 `hash_indexing_failures=588`（全部失败）的情况。

### 3.3 评测前的就绪检查（评测代码已内置）

`RagChineseQualityTest` 会先 `awaitIndexReady()`：连续 3 次检索到稳定且非空才开跑。
**没有这一步会得出错误结论** —— 实测换模型后直接测出 10%（比英文基线还差），
查 Redis 才发现 `num_docs=300`（应 588），即**索引只建了一半**（异步建库，测试跑太快）。

## 4. 已知局限（诚实说明）

| 局限 | 说明 |
|---|---|
| **口径对「排序」不敏感（最需要补的一条）** | 判定只看"Top-3 里有没有期望词"，**Top-3 内部谁排第一完全看不出来** —— §2.4 已实测到「默认参数下 Top-1 是无关商品、正确商品排第 2/3」这种情况，而指标照样满分。**要评估排序质量（如 MRR/NDCG）得另加口径**，本轮没做 |
| **原始全量的 40% 是被灌水的分母** | 20 条里 11 条的类目商品库里根本没有（§1.3）。**两个口径必须一起看**，单看任何一个都会误判：只看 40% 会低估检索能力，只看 88.9% 会忽略"真实商品库覆盖不到用户想问的类目"这个**业务事实** |
| **唯一真实的检索失败是语义组第 2 条** | 「洗完脸用来擦的」Top-3 全是「润肤**洁面**泡沫」（语义上贴「洗脸」不贴「擦的」），关键词侧 0 命中；实测扩候选集到 30 仍是 0 命中 —— **不是候选集大小的问题**，指向嵌入模型语义分辨力上限（是否值得上 bge-large-zh 需另行评估，本机内存紧张） |
| **关键词通路会被词面噪声污染** | 样板文本（「详情：商品介绍加载中…」「产品信息 Product Information」）与长品牌文案，都会让无关商品拿到与向量侧 Top-1 打平的 `1/60`，并靠"平局先插先赢"坐上 Top-1（§2.4 末，已用 `weight=0.5` 对照定位到关键词侧）。**未修**，需要排序口径才谈得上验证收益 |
| **语料只有商品维度** | 当前只索引商品（名称/分类/标签/简介/详情），**没有 FAQ / 政策类语料** —— 所以"你们支持退货吗"这类问题靠模型常识答，不走 RAG |
| **未做端到端答案质量评测** | 本评测只量**检索**；"检索到了是否答得对"需要 `CsAgentTenQuestionIT`（依赖真实上游，当前受额度限制，实测有效回答 1/10） |
| **中文分词用 2-gram** | 够用且无需引入分词器，但对长专名（如「无印良品高保湿化妆水」）的召回可能不如专业分词 |
