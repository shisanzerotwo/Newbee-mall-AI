# TASK M3-C：接入面防护（限流 + 并发上限 + 用量记账）

> **依据**：`docs/DESIGN.md` §7.2「安全与滥用防护 → 接入面」、DoD §10.1（「限流与上限生效」）
> **前置**：SSE 接口 `POST /api/cs/chat` 已上线（M2-5），且**匿名可达**
> **性质**：这是 **DoD 明确项 + 安全项** —— 当前代码注释自己写着「本接口匿名可达且暂无鉴权/限流」

## 1. 为什么必须做

`/api/cs/chat` 是**公开、匿名可达**的端点，每一次调用都会：
- 打一次上游模型（**真金白银 / 免费额度**）
- 可能触发工具循环（最多 5 轮模型调用）
- 写一行会话记忆（落库）

**无限流 = 任何人写个循环就能把额度烧光、把库写满。** M2-5 起这个端点已经对外可用，防护一直缺着。

## 4. 🔴 设计要点（容易做错的地方）

1. **超限必须给 429，不能给 200**
   本项目反复踩过「200 掩盖错误」。限流是**明确的拒绝**，必须用 HTTP 状态码表达，前端才能区分"被限流"与"模型答不出来"。

2. **限流的键怎么选**
   - 登录用户 → `userId`
   - 匿名 → 前端 `conversationId`（§7.4 已确立的会话维度）
   - **兜底**：两者都没有时用客户端 IP（否则等于没限流）
   ⚠️ 不要用 `HttpSession`：本项目**未启用 Spring Session**（session 是 Tomcat 内存态，重启即变），
   用它会导致重启后限流计数丢失（虽然对限流影响小，但与 §7.4 的既定决策不一致，别引入第二个维度）。

3. **in-flight 去重不能让正常用户卡死**
   同一个 `conversationId` 上一个请求还没结束时，新请求应**明确拒绝**（429 + 说明"上一条还在回答中"），
   而不是排队等待 —— 排队会让用户以为卡住。**必须在结束时（含异常/超时路径）释放**，否则该会话永久被锁。

4. **不要在限流器里做重活**
   它会在每个请求上被调用。用 `ConcurrentHashMap` + 原子操作，**不要**全局锁。

5. **可观测**
   被限流时要**打日志**（否则线上只看到 429，不知道是谁在刷）。用量汇总建议每分钟或每 N 次打一条。

## 5. 验收标准

1. **限流生效**：同一会话连发 15 次 → 前 10 次 200，之后 **429**（有测试）
2. **in-flight 生效**：同一会话并发发 2 次 → 1 个 200、1 个 429（有测试）
3. **不误伤**：不同会话各自独立（A 被限流不影响 B）（有测试）
4. **释放正确**：一次请求结束后，同一会话可以再次请求（有测试）—— 防止"永久锁死"
5. **用量可查**：日志里能看到请求数/被限流数/工具调用数汇总
6. 全量测试通过（现有 **143** 个不能挂）+ 冒烟 16/16
7. 真机验证：curl 连发验证 429

## 6. 不做的事

- 不做鉴权/登录态（决策 #40 只要求限流；登录态是阶段 2）
- 不做分布式限流（单机应用，不需要 Redis 计数）
- 不改 SSE 事件协议（限流发生在**建立连接之前**，用普通 HTTP 429，不走事件流）
